OWNER OVERVIEW

1. What you have

The website includes Home, About, the Shop, a persistent shopping bag, personalised jersey previews, checkout return pages and policy/contact pages. Roster buttons open Evoke’s team page on Fortnite Tracker. Local roster pages, News, Events and public customer login are not included.

Both jersey colours cost $59.99 USD. Confirmed sizes are XS, S, M, L, XL and XXL. Customers enter the name to be printed on the back. Different names remain separate bag items.

The site is built with Next.js, React, TypeScript and CSS. Public content is edited in project files. A PostgreSQL database stores private order records, Stripe takes payments, and Resend sends optional confirmation emails.

Setup status

The website and payment integration are implemented. Your own hosting, domain, database, Stripe account, delivery settings and email account still need connecting. Live account payments, database migrations and email delivery have not been verified against your accounts. Complete the launch checks in section 11 before accepting real orders.

This file is the master guide. Open it in any browser; use the browser’s Print command to print it or save a PDF. Keep it with your private project files, outside public/.

3. Open & build the website locally

Install a maintained Node.js 22 or 24 LTS release, including npm. The current project has been built with Node.js 24. Extract the client ZIP into a normal folder, then open a terminal in the folder containing package.json.

First installation

npm ci
npm run dev

Open http://127.0.0.1:3000/. Keep the terminal running. Press Ctrl+C to stop. Development mode refreshes most changes automatically.

The public pages and shopping bag work without payment credentials. Checkout shows Payment Configuration Not Setup until the required payment settings have been supplied. The bag stays intact.

Check a production build

Stop the development server first, then run:

npm run build
npm start

This is the version to review before publication. npm run typecheck is an additional check for TypeScript errors. After a code, content or image change, rebuild and restart the production version.

npm ci recreates node_modules/ from the supplied lock file. npm run build creates .next/. These generated folders are deliberately excluded from the client ZIP.

4. Upload, hosting & connecting a domain

A domain is the address; hosting runs the website.

This project needs a Next.js/Node.js server. Uploading only images or HTML to a basic public_html folder will not provide payments, order storage or staff access. A static-only host is unsuitable for the complete application.

What files should be uploaded?

Upload the clean project source to the host’s private application/project directory, or connect a private source repository. Include:

app/                    Pages, styling and server endpoints
src/                    Components, content and commerce logic
public/                 Website artwork, video and local font
migrations/             Database upgrade files
scripts/                Database migration and password tools
package.json
package-lock.json
next.config.ts
next-env.d.ts
tsconfig.json
postcss.config.mjs
.npmrc
.gitignore

Keep MASTER_SETUP.html with your private project files. Do not put secrets, database exports, fulfilment CSVs or this guide in public/. Everything under public/ is downloadable by visitors.

Do not upload your local node_modules/, .next/, *.tsbuildinfo or local secret files as public website files. The host installs dependencies and builds its own release.

Option A — hosting that supports Next.js

  1. Create a Next.js application on the host and upload/connect the source folder containing package.json.
  2. Select a supported Node.js 22 or 24 runtime. Set the install command to npm ci and build command to npm run build. Keep the host’s Next.js output setting; do not change it to a static export.
  3. Add the settings from section 5 in the host’s environment-variable/secret settings, before building.
  4. Apply the database migrations once against the intended database, through the host’s private shell or an authorised machine.
  5. If the host manages Next.js itself, use its normal server adapter. If a start command is required, use npm run start:host. It listens on the host-provided PORT, or port 3000 by default.
  6. Add the domain in the host’s dashboard, then copy its exact DNS records into your domain provider’s DNS dashboard. The host determines the required A/CNAME/verification values; there is no universal IP address to copy from this guide.
  7. Enable HTTPS. Choose one main address, with or without www, and redirect the other to it. Set both site URL settings to that main address, rebuild and restart.

Option B — run your own server

Upload the same source into a private application folder. With Node.js installed and environment settings supplied, run:

npm ci
npm run db:migrate
npm run build
npm run start:host

Run the website through your server’s service/process manager so it survives a terminal closing and restarts after a reboot. Use an HTTPS reverse proxy to route your domain to the application’s internal port. Keep the database private and use its required encrypted connection settings. Forward the original host/protocol correctly and avoid caching staff/payment responses.

Use the same canonical HTTPS domain for the shop, staff desk and webhook. A preview address and the live domain need separate matching settings. See the Next.js deployment guide for supported hosting modes.

5. Website settings

Settings are called environment variables. On your computer, create a file named .env.local beside package.json and paste the template below. Ensure Windows has not added .txt to the filename. On the live host, enter the same names and values in its private environment settings.

SettingHow to fill it
SITE_URL and NEXT_PUBLIC_SITE_URLSet both to the exact site origin, for example https://example.com, with no page path. Use the local values above only on your computer. SITE_URL takes precedence on the server.
DATABASE_URLPrivate PostgreSQL connection string supplied by the database provider, including its required TLS settings. See section 6.
STRIPE_SECRET_KEYYour account’s secret API key beginning sk_test_ for sandbox use or sk_live_ for real payments. See section 7.
STRIPE_WEBHOOK_SECRETThe signing secret for this exact webhook, beginning whsec_. It is separate from the API key.
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEYOptional for this hosted Checkout integration. Leave blank, or use the matching pk_test_/pk_live_ key. Never paste a secret key here.
JERSEY_SIZESConfirmed size list. Blank/unset falls back to XS through XXL. Only change after confirming available sizes.
SHIPPING_COUNTRIESComma-separated two-letter country codes. For example, GB,US only if shipping to both is approved. At least one supported destination is required.
Shipping rate settingsChoose one: a Stripe rate ID, a flat rate in USD cents, or FREE_SHIPPING=true. A valid Stripe rate ID takes precedence, then free shipping, then the flat rate. A flat value of 500 means $5.00 USD; it is an illustration, not an approved charge.
SHIPPING_LABELOptional customer-facing delivery label. It does not set a price or promise a delivery date.
STRIPE_AUTOMATIC_TAXUse true only after configuring Stripe Tax and the merchant’s registrations. false disables automatic tax calculation; it does not declare sales tax-exempt.
STRIPE_TAX_BEHAVIORexclusive adds applicable tax; inclusive treats it as included. Confirm the merchant’s pricing approach before changing.
PREORDER_NOTICEYour approved 20–1,200-character payment, production and dispatch disclosure. Put the complete text on one line. It appears in the purchase flow and Stripe Checkout.
Colour availabilityBLACK_JERSEY_AVAILABLE and WHITE_JERSEY_AVAILABLE default to true. Setting one to false blocks server checkout for that colour; it does not automatically remove its catalogue card.
Email and staff settingsSee sections 8 and 9. CONTACT_EMAIL is the public support address, separate from the sending service.

In a local environment file, wrap text containing spaces or a # in double quotes, for example ORDER_EMAIL_FROM="Evoke <orders@example.com>". In a host dashboard enter the value itself unless the host requests file-style quoting.

Restart after server-setting changes. Rebuild when changing public settings, content used by built pages, the contact email, or the site domain. The contact page reads CONTACT_EMAIL at build time. Public values beginning NEXT_PUBLIC_ can also be embedded during the build; see Next.js environment-variable guidance.

6. Set up the order database

  1. Create an empty PostgreSQL database with your chosen provider, preferably close to the website’s hosting region.
  2. Copy its application connection string into DATABASE_URL. Use the provider’s required TLS/encryption settings. If it offers several pooler modes, use a Node.js-compatible direct or session-pooled connection.
  3. Check the website host can reach the database. Allow only the necessary host/network access.
  4. From the project folder with those settings loaded, run npm run db:migrate.
  5. Confirm the command reports that migrations are up to date, then build/start the website.

The migration command loads a local .env.local automatically, or uses environment variables supplied by the host. It applies the numbered SQL files in order and records their checksums. Keep migrations/ and scripts/migrate.mjs; they are required operational files.

For an existing store, back up the database before upgrades. Do not edit a migration that has already run. For future database changes, add a new numbered migration. Do not replace a live order database with an empty development database.

Orders include the printed name, colour, size, quantity, prices, Stripe references, contact/shipping details and fulfilment status. Public About content remains in a local JSON file.

7. Set up Stripe payments

Connect the merchant account

  1. Create/sign in to Evoke’s Stripe account and complete its business, bank/payout, identity and customer-support settings.
  2. Start in a Stripe sandbox. Put that account’s sk_test_ key into STRIPE_SECRET_KEY. Keep sandbox and live credentials separate. The current application accepts account secret keys in sk_test_/sk_live_ format. Restricted and organisation keys are not supported by this version.
  3. Configure the approved shipping destinations and one rate method from section 5. If using a Stripe shipping rate ID, ensure its currency is USD and it belongs to the same sandbox/live environment as the key.
  4. Add the approved PREORDER_NOTICE and configure tax settings. The public policy pages must describe the same commercial terms.
  5. Create the webhook below, then rebuild/restart after updating the environment.

The server creates the jersey line items and prices. You do not need to manually create Stripe product or price IDs for the current catalogue. Hosted Stripe Checkout collects payment and shipping details; no card numbers are stored by this website.

Create the payment webhook

A webhook is Stripe’s private notification to the website that a payment or refund has changed. It must work even if the customer closes their browser.

  1. In Stripe, open Workbench/Webhooks and create an event destination for your account. Dashboard wording may vary.
  2. Choose Snapshot payloads for this implementation and a webhook endpoint destination.
  3. Enter https://example.com/api/stripe/webhook, replacing the example domain with your real canonical domain.
  4. Select these exact event types:
checkout.session.completed
checkout.session.async_payment_succeeded
checkout.session.async_payment_failed
checkout.session.expired
charge.refunded

Copy this endpoint’s signing secret into STRIPE_WEBHOOK_SECRET. A sandbox endpoint and live endpoint have different secrets. The endpoint must be publicly reachable over HTTPS, without a staff login or redirect in front of it. See Stripe’s webhook instructions.

Check the complete order journey

Using the sandbox and Stripe’s official sandbox payment details, purchase each colour with different printed names. Confirm the names, sizes and quantities in the bag, in hosted Checkout and in the staff order desk. Check shipping/tax amounts and confirmation email delivery. Check cancellation, a declined payment and a refund. Redelivering a payment event must not duplicate the order.

For local checks, install the official Stripe CLI, sign in to the correct sandbox and run stripe listen --forward-to http://127.0.0.1:3000/api/stripe/webhook. Use the listener’s signing secret locally. Complete an actual sandbox checkout through the Evoke shop; an unrelated synthetic event has no matching Evoke order.

Switch on real payments

After successful sandbox checks, set the real sk_live_ key, matching optional publishable key, live webhook secret and live shipping rate if applicable. Rebuild/restart and confirm the live webhook is active. See Stripe’s key guide. No separate hidden checkout-enable switch is required.

Issue refunds from the Stripe Dashboard. The signed refund event updates the website’s order record. A staff fulfilment change does not create a refund. Review partially refunded orders before manufacturing.

8. Set up confirmation emails and support

  1. Create a Resend account owned by Evoke. Add the domain or dedicated sending subdomain you will use.
  2. In the domain’s DNS dashboard, add the exact verification/DKIM/SPF records Resend supplies. Do not replace existing mailbox MX records with unrelated values. Wait until Resend reports the sending domain as verified.
  3. Create a sending API key and store it privately as RESEND_API_KEY.
  4. Set ORDER_EMAIL_FROM to an address on the verified domain, for example Evoke <orders@example.com>. Use your actual domain.
  5. Set CONTACT_EMAIL to your working customer-support mailbox. Creating a sending identity does not create a mailbox for reading replies; arrange that separately with your email provider.
  6. Restart/redeploy, complete a sandbox order and check the provider log and recipient inbox/spam folder.

The confirmation contains the order reference, jersey colour, size, printed name, quantity, amount paid and pre-order disclosure. The sending address is also the normal reply destination unless your provider supplies different handling. Use a monitored mailbox if customers should reply there.

Without a configured email provider, a paid order remains recorded. The website does not pretend an email was sent. Staff can inspect delivery status and retry after correcting the settings. sent means the provider accepted the message, not guaranteed inbox arrival.

Automatic delivery attempts are bounded. A staff retry uses the same per-order provider idempotency key; after an ambiguous delivery, check provider records before retrying, particularly after 24 hours. Stripe’s payment receipt is a separate account setting.

Official help: verify a Resend domain and manage Resend API keys.

9. Staff access & managing orders

Create the private staff password

In an interactive terminal in the project folder, run:

node scripts/hash-admin-password.mjs

Enter a strong password of at least 16 characters. Input is hidden. The tool prints an ADMIN_PASSWORD_HASH=... line. Save only the value after = in the host’s ADMIN_PASSWORD_HASH setting. Store the actual password in Evoke’s password manager for authorised staff.

Generate a separate signing secret:

node -e "process.stdout.write(require('node:crypto').randomBytes(48).toString('hex'))"

Save the output as ADMIN_SESSION_SECRET. Keep it separate from the password. A configured database and exact site URL are also required for staff access. Restart after setting these values.

Open the order desk

Visit https://example.com/admin/orders on your real domain and sign in. There is no public navigation link. Sessions last up to eight hours; staff should sign out when finished.

How staff accounts work

The current version uses one shared staff password. It does not provide named accounts, invitations, individual permissions or a password-reset email. Only trusted fulfilment staff should receive access.

Everyday order workflow

  1. Open paid pre-orders and expand an order to review the printed name, colour, size, quantity, payment reference and shipping details.
  2. Export the fulfilment CSV when preparing a production batch. It contains private customer information; give it only to the intended fulfilment/manufacturing team.
  3. Check the exact spelling and approve the supplier’s physical print proof. The live preview records the name but does not define centimetre measurements.
  4. Update the order from Paid — Pre-order to In production, then Dispatched and Fulfilled, as appropriate. Add the carrier/tracking reference when available.
  5. If the confirmation email failed, correct the email setup and use Retry confirmation email.

The CSV includes paid and partially refunded order lines and excludes fully refunded ones. Review partial refunds before production. For more than 10,000 order lines, use your database provider’s export tools. Fulfilment edits are logged. Updating fulfilment does not send a separate dispatch/tracking email in the current version.

Change or revoke access

Run the password tool again to set a new hash. Rotate ADMIN_SESSION_SECRET as well to invalidate all existing sessions, then restart. There is no email recovery route; authorised hosting access is needed to change these settings.

11. Before accepting real orders

  • The canonical domain opens over HTTPS and the alternative www/non-www address redirects correctly.
  • Both site URL settings use that exact main domain.
  • Database migrations are applied; backups are enabled and a restore procedure is available.
  • Stripe sandbox orders have completed for both colours and different printed names.
  • The staff desk contains the correct immutable names, sizes, quantities, addresses and paid totals.
  • Webhook delivery/retry, payment failure, cancellation and refund behaviour have been checked.
  • The approved shipping destinations, charges, production/dispatch disclosure and applicable tax treatment are configured.
  • Shipping, returns, terms, privacy and contact pages contain the real merchant details.
  • The sending domain is verified, the confirmation email arrives, and customers have a working support mailbox.
  • Staff can sign in, inspect/export orders, update fulfilment and sign out.
  • Phone and desktop navigation, video, product previews, name editing and the bag have been reviewed.
  • Live Stripe keys, live webhook secret and live shipping rate have replaced sandbox values in production.
  • The production build succeeds and the server remains running after the deployment terminal closes.

Your project ZIP contains the website source and this guide, without preview screenshots or local dependencies. Complete the live service checks above before accepting orders.

12. Updates, backups & ownership

Keep a private backup/version history of the source and artwork. Enable database backups with your provider and occasionally verify that a restore works. Rebuilding the website does not back up customer orders.

Keep secrets in the host’s secret settings and Evoke’s password manager. Share fulfilment exports only with authorised staff/suppliers, and follow your customer-data retention policy. Rotate credentials if access is lost or a staff member leaves.

Before updating dependencies or changing the database, take a backup, review the change on a separate preview, build it and check the order journey. Keep package-lock.json; it records the dependency versions. Avoid updating packages on the live server without a reviewed release.

Hosting, domain renewal, database, Stripe and email-service accounts should all be recoverable by Evoke. Record the account owners and renewal/billing arrangements in your private business records, not in a public website folder.

13. Troubleshooting
